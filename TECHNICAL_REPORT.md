# Technical Architecture & System Report

**Project:** Manju Sensei — Teacher's Resource Hub
**Type:** Static single-page application with a managed backend
**Stack:** Vite 5 · React 18 · Tailwind CSS 3 · Supabase (PostgreSQL, Storage, Auth) · Google AI Studio (Gemini REST)
**Hosting:** Netlify (static build, SPA fallback)
**Report date:** 1 November 2026

---

## 1. Executive summary

This system gives a single senior teacher a public, editorial-quality home for study material, a direct WhatsApp-first contact channel, and a three-screen admin console — without a server, a CMS licence, or a monthly hosting bill.

It is deliberately small. The public surface is one page with four anchored sections; the private surface is one console with three screens. Everything persistent lives in Supabase, guarded by Row Level Security. Everything rendered is a static asset served by Netlify's CDN.

Three engineering decisions define the build:

1. **Zero-backend architecture.** No custom API server exists. The browser talks to Supabase over HTTPS using the public anon key; RLS is the security boundary, not application code.
2. **Retention as a product feature.** Student messages are treated as ephemeral by design, deleted after seven days by three independent mechanisms, so the free tier cannot silently accumulate personal data.
3. **Identity-locked AI.** Sleep Sensei is a Gemini-backed assistant wrapped in a system instruction and a response sanitizer that prevent it from disclosing its underlying provider, while keeping answers scoped to Class 7–10 Hindi, Sanskrit and general tuition subjects.

| Dimension | Result |
| --- | --- |
| Runtime dependencies | 4 (`react`, `react-dom`, `@supabase/supabase-js`, `lucide-react`) |
| Database tables | 2 (`resources`, `messages`) |
| Storage buckets | 1 (`resources`, public read / authenticated write) |
| Admin screens | 3 (upload, manage, inbox) |
| Auth model | Supabase email + password, case-normalised |
| Message retention | 7 days, triple-enforced |
| Server cost | ₹0 on free tiers (Netlify + Supabase + AI Studio) |

## 2. System overview & design philosophy

### 2.1 The "Editorial Studio" aesthetic

The visual language is a deliberate reaction against generic school portals: no blue gradients, no card shadows copied from a dashboard kit, no stock classroom photography. The page reads like a printed cultural supplement that happens to be interactive.

| Token | Value | Role |
| --- | --- | --- |
| Canvas | `#F4F1EA` | Warm alabaster base; softer than white on phone screens |
| Ink | `#0E0C15` | Primary text, pill buttons, obsidian surfaces |
| Ink soft | `#13101E` | Secondary dark surface |
| Plum | `#1F133D` | Top of the active-card gradient |
| Obsidian | `#0C0914` | Bottom of the active-card gradient |
| Purple | `#6D3DF2` | Highlight blocks, arrows, progress, stars |
| Purple light | `#7C4DFF` | Hover and glow states |
| Muted | `#6E6A7C` | Metadata, helper copy |
| Hairline | `rgba(14,12,21,0.12)` | 1px card and section borders |

Two ambient layers sit behind all content:

- A fixed **radial mesh** with three lavender/violet emitters (`rgba(109,61,242,0.11–0.16)`) and two slowly drifting blur orbs.
- A fixed **grain layer** generated by an inline SVG `feTurbulence` filter at 5% opacity with `mix-blend-mode: multiply`, which removes the flatness of large cream areas.

Both are `pointer-events: none` and excluded from the accessibility tree.

### 2.2 Typography hierarchy

| Family | Weights | Used for | Treatment |
| --- | --- | --- | --- |
| **Instrument Serif** | 400, 400 italic | H1–H3, footer wordmark, large numerals | Tight tracking (`-0.025em`), 0.94–0.98 line height, upright/italic alternation inside single headings |
| **Plus Jakarta Sans** | 200–800 variable | Body, buttons, form fields | 400 body, 500–600 controls, relaxed 1.55–1.7 line height |
| **JetBrains Mono** | 400, 500 | Index tags, dates, badges, metadata | Uppercase, `letter-spacing: 0.14em`, 0.46–0.65rem |

Every major heading mixes an upright serif phrase with an italic serif phrase — *"Two tracks. One obsession with clarity."*, *"Let's learn."* — which is the signature of the editorial direction. A serif italic accent is also used for the track subtitles and the purple highlighted word.

### 2.3 Interactive state mechanics

The design is built around four repeatable interactions rather than decorative animation:

| Interaction | Trigger | Implementation |
| --- | --- | --- |
| Tilted highlight block | Tap/click the word "Knowledge." or "learn." | `.word-tap` toggles `.is-on`; a `::before` block rotates `-1.5deg` and scales in with a spring curve; text becomes white |
| Colour burst + accent shift | Tap any `✦` glyph | Eight seeded particles animate along radial vectors; a `accent:cycle` window event rotates `--purple` through four shades, changing every highlight, progress bar and orb live |
| Card colour morph | Tap any track, method, or resource card | `.is-active` swaps the surface to `linear-gradient(145deg,#1F133D,#0C0914)`, flips typography to cream, illuminates the top-right orb purple, and brightens the pill tags |
| Scroll progress | Page scroll | A 3px fixed gradient bar with a glowing leading spark, updated through `requestAnimationFrame` |

Supporting motion: card lift on hover, 45° orb rotation, a pausable subject marquee, a slowly rotating hero star, a scroll-reveal system, and staggered section entrances. All of it collapses under `prefers-reduced-motion: reduce`.

## 3. Frontend architecture

### 3.1 Composition

```text
main.jsx
└── App.jsx                     scroll progress · reveal observer · accent shift · auth session
    ├── Navbar.jsx              sticky glass header · hex-core logo · admin entry
    ├── HeroEditorial.jsx       metadata rail · interactive headline · tilt card · marquee
    ├── AcademicTracksBento.jsx two morphing track cards + method card
    ├── ResourceVault.jsx       search · filters · cards · preview modal (portal)
    ├── ContactSection.jsx      WhatsApp panel + validated message form
    ├── FooterEditorial.jsx     "Let's learn." interaction · contact grid · admin entry
    ├── SleepSenseiChat.jsx     floating trigger · right-hand drawer · chat state
    └── admin/
        ├── AdminLoginModal.jsx      normalised email/password auth
        └── AdminDashboard.jsx       tab shell · counts · session chrome
            ├── UploadResourceScreen.jsx
            ├── ManageResourcesScreen.jsx
            └── MessagesInboxScreen.jsx
```

No router is used. The site is a single document with four anchors (`#tracks`, `#vault`, `#contact`, `#top`). The admin console is a full-viewport overlay rather than a route, which keeps the deployment a pure static bundle with no history-rewrite edge cases (though `netlify.toml` still provides an SPA fallback).

### 3.2 State ownership

| State | Owner | Notes |
| --- | --- | --- |
| Scroll progress | `App` | Single passive listener, rAF-throttled |
| Auth session | `App` | Hydrated by `getSession()`, kept in sync by `onAuthStateChange` |
| Console open/closed | `App` | Clears the chat drawer when opened |
| Vault refresh signal | `App` | Integer version bumped by admin mutations |
| Chat drawer state | `App` | Passed to hero and chat component |
| Resource data | `ResourceVault` | Re-fetches when `refreshKey` changes |
| Admin resource data | `ManageResourcesScreen` | Independent fetch; reports changes upward |
| Message data | `MessagesInboxScreen` | Independent fetch + expiry filter |
| Accent colour | `App` | CSS custom properties on `:root`, driven by a custom event |

The only cross-component signal is a `refreshKey` integer. When an upload or delete succeeds in the console, `App` increments it and the public vault reloads in the background, so the two views never disagree after the overlay closes.

### 3.3 Data access layer

`src/lib/supabaseClient.js` centralises:

- **Client creation** behind an `isSupabaseConfigured` guard that treats placeholder values as "not configured", so a preview without secrets renders guidance instead of throwing.
- **Auth persistence** under the scoped storage key `manju-sensei-auth`.
- **Retention** via `purgeExpiredMessages()` — RPC first, direct delete fallback.
- **Formatting** for dates (`en-IN`), relative expiry days, and byte sizes.
- **File intelligence** — MIME/extension normalisation to `pdf | image | doc`, safe storage paths that preserve extensions even for Devanagari filenames, and download-URL construction.
- **Error translation** — PostgREST and Auth errors become human sentences ("The database tables are missing. Run the migration file in Supabase.").

### 3.4 Mobile-first responsiveness

- Layouts are single-column below 768px and use a 12-column grid above it. The hero and contact sections switch at `lg`.
- Typography uses `clamp()` so headings scale continuously instead of stepping.
- Filter chips and the admin tab bar are horizontally scrollable with hidden scrollbars.
- The admin console uses a **bottom tab bar on mobile** and a **top tab bar on desktop**; main content reserves bottom padding for the fixed bar and `env(safe-area-inset-bottom)`.
- All interactive targets are at least 36–44px; the chat input and send orb sit above the keyboard.
- Dialogs lock body scroll, close on Escape, and close on backdrop tap.
- The chat drawer takes the full width on phones and 27rem on desktop.

### 3.5 Accessibility

- Semantic landmarks (`header`, `nav`, `main`, `section`, `footer`), one `h1`, ordered headings.
- A skip link targets the vault.
- Icon-only controls carry `aria-label`; filter and tab state use `aria-pressed` / `aria-current`.
- The preview dialog uses `role="dialog"`, `aria-modal="true"` and a labelled title.
- Focus-visible rings use the purple accent at 2px with offset.
- Motion respects `prefers-reduced-motion`.
- Colour contrast: ink on alabaster is ~16:1; cream on obsidian is ~15:1; purple on cream is ~4.6:1 for large display type and used with weight/size rather than for body copy.

### 3.6 Performance

- Production bundle is a single Vite build with tree-shaken Lucide icons and no chart, date, or form libraries.
- No web fonts are self-hosted; the three Google Fonts families load with `display=swap`, preconnect hints and only the weights used.
- Images in the vault are `loading="lazy"`.
- Scroll work is rAF-throttled; reveal work is delegated to a single `IntersectionObserver` plus a `MutationObserver` so dynamically loaded cards animate without per-card observers.
- The Supabase client and Gemini requests are made only when the relevant UI is used.

## 4. Backend & security architecture

### 4.1 Schema

```sql
public.resources
  id            uuid      primary key default gen_random_uuid()
  title         text      not null, 1–160 chars
  category      text      not null default 'General'
  file_url      text      not null
  storage_path  text
  file_type     text      not null, check in ('pdf','image','doc')
  file_size     bigint
  created_at    timestamptz not null default now()

public.messages
  id            uuid      primary key default gen_random_uuid()
  sender_name   text      not null, 1–120 chars
  sender_phone  text      not null, 6–24 chars
  sender_email  text      (nullable)
  message_text  text      not null, 1–4000 chars
  created_at    timestamptz not null default now()
```

Indexes: `resources(created_at desc)`, `resources(lower(category))`, `messages(created_at desc)`.

`file_url` is a public Storage URL; `storage_path` is retained so deletion can remove the object, not just the row. The split is deliberate: public reads never need to list the bucket, while the admin can still address the exact object.

### 4.2 Storage

One public bucket, `resources`:

- 25 MB per-object limit.
- Explicit MIME allowlist covering PDF, JPEG, PNG, WebP, GIF, HEIC, Word, PowerPoint, plain text, plus `application/octet-stream` for browsers that do not report a type.
- Public `SELECT` so resource links work for logged-out students.
- `INSERT`, `UPDATE`, `DELETE` restricted to the `authenticated` role — meaning the teacher's session, not a hard-coded key.
- Upload paths are `{timestamp}-{random}-{safe-name}.{ext}` to prevent collisions and path traversal.

### 4.3 Row Level Security matrix

| Table / object | anon SELECT | anon INSERT | anon DELETE | authenticated SELECT | authenticated INSERT | authenticated UPDATE | authenticated DELETE |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `public.resources` | ✅ all | ❌ | ❌ | ✅ all | ✅ | ✅ | ✅ |
| `public.messages` | ❌ | ✅ | ⚠️ expired only | ✅ all | ✅ | ❌ | ✅ |
| `storage.objects` (`resources`) | ✅ | ❌ | ❌ | ✅ | ✅ | ✅ | ✅ |

The `⚠️` row is the cleanup policy: anonymous visitors may delete **only** rows whose `created_at` is already older than seven days. They cannot read them, cannot delete recent ones, and cannot enumerate the table.

Grants are written explicitly alongside the policies so the migration does not depend on project-specific default privileges.

### 4.4 Authentication pipeline

The admin account is a real Supabase Auth user, seeded by the migration as a bcrypt hash (`crypt('manjusensei', gen_salt('bf'))`) with `email_confirmed_at` set. No password exists in source code, no environment variable, and no client bundle.

```js
// AdminLoginModal.jsx
const normalizedEmail = email.trim().toLowerCase()
const normalizedPassword = password.trim().toLowerCase()

const { data, error } = await supabase.auth.signInWithPassword({
  email: normalizedEmail,
  password: normalizedPassword,
})
```

Why normalise the password? The stored password is lowercase. Supabase compares the raw string, so `ManjuSensei` would otherwise fail. Lowercasing both inputs makes every capitalisation of the same password succeed — including mobile keyboards that auto-capitalise the first letter. The trade-off is documented in the setup guide: the admin password itself must remain lowercase.

Session lifecycle:

1. `getSession()` hydrates `App` on load (localStorage, scoped key).
2. `onAuthStateChange` keeps the session current across token refresh and sign-out.
3. The console renders only when `session` is truthy; otherwise the login modal renders in its place.
4. Sign-out calls `supabase.auth.signOut()` and closes the overlay.
5. RLS makes the session meaningful: an attacker with the anon key can read resources and insert messages, but cannot write resources, read messages, or touch storage objects.

### 4.5 Threat model and limits

| Threat | Mitigation |
| --- | --- |
| Anon key scraped from bundle | Expected; RLS is the control. Only public reads and message inserts are exposed |
| Message spam | Form validation, DB length checks, 7-day purge. No captcha — a deliberate simplicity trade-off for a single-teacher site |
| Upload of executable content | MIME allowlist + extension allowlist + `file_type` constraint; bucket is served as static objects |
| Student data retention | 7-day automatic deletion, three layers deep |
| Credential leakage | No password in repo or env; bcrypt hash lives in `auth.users` |
| XSS via resource titles / messages | React escapes all interpolated strings; no `dangerouslySetInnerHTML` anywhere |
| Malicious file names | Storage paths are sanitised to `[a-z0-9-]` with the original extension preserved |

Known limitations: there is no rate limiter on the contact form, no email notification on new messages, and no server-side moderation of AI answers. All three are acceptable for a single-teacher hub and are noted in §9.

## 5. Automated data retention pipeline

### 5.1 Objective

A free-tier Supabase project should never accumulate personal data indefinitely. The requirement is a hard seven-day ceiling on `public.messages`, enforced without an operator remembering to press anything.

### 5.2 Three independent layers

```text
             ┌─────────────────────────────────────────────┐
 INSERT ───▶ │ 1. AFTER INSERT trigger                     │
             │    delete_expired_messages()                │
             │    DELETE ... < now() - interval '7 days'   │
             └─────────────────────────────────────────────┘
             ┌─────────────────────────────────────────────┐
 03:15 ────▶ │ 2. pg_cron job "purge-expired-messages"     │
             │    (skipped safely if pg_cron is absent)    │
             └─────────────────────────────────────────────┘
             ┌─────────────────────────────────────────────┐
 App load ─▶ │ 3. Client: purge_expired_messages() RPC     │
 Inbox load  │    fallback: .delete().lt('created_at', …)  │
             └─────────────────────────────────────────────┘
```

**Layer 1 — trigger.** `delete_expired_messages()` is a `SECURITY DEFINER` function that runs `AFTER INSERT` for each row. It does not care who inserted the message; it leaves only rows inside the window. Because it is defined with `set search_path = public`, it cannot be hijacked by a caller-controlled search path.

**Layer 2 — cron.** When `pg_cron` exists, a daily job at 03:15 runs the same predicate. The scheduling block is wrapped in `DO $$ … EXCEPTION WHEN OTHERS THEN NULL; END $$;` so a project without the extension completes the migration with a notice instead of an error.

**Layer 3 — client.** Both the public page and the admin inbox call `purge_expired_messages()` on load. That RPC is `SECURITY DEFINER` and limited to the expired predicate, so it is safe to expose to `anon`. If the RPC is unavailable (partially applied migration), the client falls back to the exact delete the specification requires:

```js
supabase.from('messages').delete().lt('created_at', sevenDaysAgoISO)
```

The inbox additionally filters fetched rows client-side, so a message is never displayed after its window even if every cleanup layer were somehow delayed.

### 5.3 Why `SECURITY DEFINER` is safe here

The function can only execute one fixed statement. It takes no parameters, returns a count, and cannot be influenced by the caller beyond the current timestamp. `EXECUTE` is granted to `anon` and `authenticated` explicitly and revoked from `PUBLIC`. The alternative — granting `anon` broad `DELETE` on `messages` — would be strictly worse.

### 5.4 Failure modes

| Failure | Effect | Recovery |
| --- | --- | --- |
| `pg_cron` unavailable | Trigger and client still purge | None needed |
| Client offline | Rows persist until the next visit or cron run | Next visit |
| Migration partially applied | RLS denies deletes; inbox still hides stale rows | Re-run migration |
| Clock skew | Boundary rows may live a few minutes longer | Acceptable |

## 6. Sleep Sensei AI architecture

### 6.1 Request path

```text
Chat drawer
  └── askSleepSensei({ history, message })
        ├── builds system_instruction + contents (last 14 turns)
        ├── attempts gemini-2.5-flash
        ├── on model-unavailable → gemini-2.0-flash
        ├── on 429 / auth / safety → typed error, no retry
        └── sanitizeIdentity(reply) → drawer
```

The call goes directly from the browser to:

```text
POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent
x-goog-api-key: VITE_GEMINI_API_KEY
```

Payload shape:

```json
{
  "system_instruction": { "parts": [{ "text": "<identity lock>" }] },
  "contents": [
    { "role": "user", "parts": [{ "text": "…" }] },
    { "role": "model", "parts": [{ "text": "…" }] }
  ],
  "generationConfig": {
    "temperature": 0.7,
    "topP": 0.9,
    "topK": 32,
    "maxOutputTokens": 1200
  }
}
```

### 6.2 Prompt engineering

The system instruction does three jobs:

1. **Defines the persona** — Sleep Sensei, a warm academic mentor for Class 7–10 Hindi, Sanskrit (Vyakaran, translations, shlokas, literature) and general tuition subjects.
2. **Locks the identity** — the exact rule is embedded verbatim, including the canned reply that must be used when asked about its model or provider.
3. **Sets pedagogy** — numbered steps, rule → worked example → practice question for grammar, reasoning before the final answer for Maths and Science, board-answer structure, and a refusal to invent page numbers, mark schemes or school notices.

The rule text is intentionally duplicated in code and report so any future edit is obvious in review.

### 6.3 Defence in depth

Prompt instructions are not a security boundary, so `sanitizeIdentity()` runs on every returned string. It matches direct claims (`I am Gemini`, `as a large language model`), provider credits (`trained by Google`, `powered by OpenAI`), and brand mentions (`ChatGPT`, `OpenAI`). On a match it returns the canonical identity line plus a redirect back to the study question.

| Layer | Prevents |
| --- | --- |
| `system_instruction` | Most identity disclosure and scope drift |
| Response sanitizer | Model drift, prompt-injected jailbreaks, provider leakage |
| History cap (14 turns) | Context bloat and accidental instruction replay |
| Model fallback | Single-model outages / deprecations |
| Typed errors | Leaking raw provider JSON to students |

### 6.4 Cost and failure behaviour

The assistant uses the AI Studio free tier with a browser-held key. That key is public by necessity; it is rate-limited by Google and should be treated as expendable. Responses are capped at 1,200 output tokens, history at 14 messages, and there is no server-side proxy — so there is no way to hide the key from a determined user. For a single classroom this is an acceptable trade-off; a production multi-tenant build would proxy through an edge function and keep the key server-side.

Failure handling is explicit:

- Missing key → the drawer shows a setup card and disables the composer.
- `429` / quota → "Sleep Sensei has answered a lot of questions today…"
- `401` / `403` → key rejected message.
- Safety block → asks the student to rephrase.
- Empty candidate → asks again.
- Network failure → connection message.

## 7. Deployment & operations

### 7.1 Build pipeline

```text
GitHub push → Netlify build (Node 20)
  ├── npm install
  ├── npm run build   → tsc not required (plain JSX)
  └── publish dist/
```

`netlify.toml` pins the build command, publish directory, Node 20, SPA fallback (`/* → /index.html`), immutable caching for hashed assets, and baseline security headers (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`).

### 7.2 Environment variables

| Variable | Required | Exposure |
| --- | --- | --- |
| `VITE_SUPABASE_URL` | Yes | Public (project URL) |
| `VITE_SUPABASE_ANON_KEY` | Yes | Public (RLS-protected) |
| `VITE_GEMINI_API_KEY` | For AI | Public (AI Studio key) |
| `VITE_GEMINI_MODEL` | No | Public (model id) |

Vite inlines `VITE_*` values at build time. Changing any value requires a redeploy, not just a restart.

### 7.3 Operational runbook

| Task | Where | Frequency |
| --- | --- | --- |
| Publish material | Console → Upload | As needed |
| Remove material | Console → All resources → Delete | As needed |
| Answer students | Console → Inbox → Reply on WhatsApp | Daily / weekly |
| Verify retention | Inbox → Purge expired | Monthly |
| Rotate admin password | Supabase Auth → Users | Quarterly |
| Check AI quota | AI Studio dashboard | Monthly |
| Review Netlify builds | Netlify deploys | On change |

## 9. Limitations & future work

**Deliberate exclusions (per the brief):** no class timetable, no results, no testimonials, no student accounts. The site is a resource hub, not a school ERP.

**Current limitations:**

1. The Gemini key is browser-visible; a proxy would be required for multi-teacher use.
2. The contact form has no captcha or IP rate limiting.
3. Resource uploads are single-file; batch upload is not implemented.
4. There is no email or push notification when a message arrives.
5. Search is client-side over the loaded resource set (fine for hundreds of files, not thousands).
6. `pg_cron` availability depends on the Supabase plan; the trigger and client remain the guarantees.

**Sensible next steps, in order of value:**

1. Add an email notification (Supabase Edge Function + transactional email) for new messages.
2. Add PDF thumbnails generated on upload for a richer vault.
3. Add a lightweight analytics event on resource downloads to learn what students actually use.
4. Move AI calls behind an edge function to protect the key and add per-student quotas.
5. Add offline caching (service worker) for previously opened resources on weak mobile networks.

## 10. Conclusion

The system is intentionally narrow and unusually polished for its size: a fully static front end, a two-table Postgres backend protected by RLS, a three-layer retention pipeline that makes privacy the default, and an AI assistant whose identity and scope are enforced in two places.

It can be deployed from a phone in about half an hour, operated by one teacher, and maintained by editing a single configuration file. That combination — editorial design, minimal architecture, and explicit data hygiene — is the actual deliverable.
